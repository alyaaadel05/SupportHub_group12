INTENDED PROJECT DESIGN (re-review)
  The microservice design implemented by the Editorial Service (README "Flag
  outdated articles", docs/test-plan.md F12, frontend/js/editorial.js "Flag as
  Outdated", frontend/js/editorial-extras.js "resolve with an explanation",
  services/editorial-service/services/flagService.js):
    published article --POST /api/articles/:id/flags (editor/admin)--> OPEN flag
      = item in the editors' re-review queue  GET /api/editorial/flags
    OPEN flag --PATCH /api/flags/:id {resolution} (independent editor)--> RESOLVED
      (resolution = "what was updated or why no change is needed")
  The article stays PUBLISHED and searchable while the re-review is open: the
  Article Service state machine has no published->outdated transition
  (allowed: draft->in_review, in_review->draft|approved, approved->published|draft,
  published->draft). The legacy monolith in backend/ set articles.status='outdated';
  that path is not part of the deployed microservice design and was intentionally
  NOT reintroduced (it would change Alyaa's Article state machine and production
  behaviour).

DEFECTS FOUND
  D1 (FIXED) Duplicate outdated requests created duplicate re-reviews.
     POST /api/articles/:id/flags always INSERTed a new open flag.
  D2 (FIXED) Self re-review was possible. The author of an article (the admin
     role can both author and review) could resolve the re-review of their own
     article, unlike publication, which already returns 403 "Cannot publish
     your own article".
  N1 (NOT A DEFECT - test expectation corrected) /api/articles/1%20OR%201=1/flags
     returned 404, not 400: the same-origin proxy (frontend/dev-server.js) only
     forwards numeric ids (/^\/api\/articles\/\d+\/flags$/) to Editorial, so the
     request never reaches Editorial or SQL. No row was created (verified).
  The other 2 baseline failures were consequences of D1/D2.

CHANGES IMPLEMENTED (Claude-assisted, Phase 4)
  services/editorial-service/migrations/008_flag_one_open_per_article.sql (NEW)
    - closes pre-existing duplicate open flags NON-destructively (keeps the
      oldest open flag; the others are resolved with "Duplicate of open flag #N
      (closed by migration 008)"; nothing is deleted), then creates the partial
      unique index editorial_flags_one_open_per_article ON (article_id) WHERE status='open'.
  services/editorial-service/services/flagService.js
    - flag(): INSERT ... ON CONFLICT (article_id) WHERE status='open' DO NOTHING;
      on conflict returns the existing open flag with duplicate=true (atomic and
      race-safe; one retry if the open flag is resolved in between).
    - resolve(): loads the flag first (404 / 409 unchanged), asks Article Service
      for the author and rejects self re-review with 403; fails closed if Article
      Service is unavailable; the UPDATE ... WHERE status='open' keeps the
      concurrent-resolution 409.
  services/editorial-service/controllers/flagController.js

      200 {flag, duplicate:true} when an open re-review already exists.

REMAINING LIMITATIONS
  - Re-review does not change articles.status (it stays 'published'), by design
    of the current Article state machine. If the team wants outdated articles
    hidden during re-review, Article Service needs a published->outdated
    transition and Editorial must call Search POST /internal/unpublications
    (exists, currently unused). Not implemented: outside Phase 4 scope.
  - A duplicate report returns the existing open flag; the second reporter's
    reason text is not stored (the response says duplicate:true).
  - Migration 008 was applied ONLY to the isolated database. Shared Neon
    development / production databases were NOT touched. Applying it there
    (npm run db:migrate with the documented safety gate) is a manual step and
    MUST precede deploying the new flagService.js (ON CONFLICT needs the index).
  - Baseline article 233 keeps flag #3 open (isolated test data); it is
    resolved through the API after the restart test (03, section C).
